# V38 polyglot experiment and vault device-proof components

Status: isolated review components, NOT deployed vault login. No Web3Vault frontend handler was located by indexed search. No enrollment route, HTTP endpoint, session issuer, key custody, production rate-limit policy or live Redis binding is installed by these files.

`polyglotSignatureKDF.ts` retains the requested compatibility filename but re-exports a non-cryptographic experiment. It is disabled unless both `enabled` and `inputIsPublic` are exactly true. It accepts three public English words and asks a fixed loopback Ollama endpoint/model for three structured nine-item transformations. No Redis/vector upload, logging, cloud fallback, wallet seed input, key derivation or access grant is implemented. Acknowledging public input does not detect accidental secret input; callers must never supply credentials or wallet recovery material. Model installation/capabilities are not verified. Fixed sampling parameters are not a cryptographic determinism guarantee. JavaScript/model runtimes cannot promise memory wiping or untraceability. Cancellation is best-effort.

`vaultDeviceAuth.mjs` implements device Ed25519 proof verification, NOT WebAuthn/passkeys. A trusted server must resolve tenant/user/pre-auth-session context, enforce permission/rate limits, and retrieve already enrolled, enabled, vault-scoped public keys. Enrollment must independently verify ownership and proof of possession. Never auto-enroll keys from a login request, accept client plan/admin flags, or use wallet signing keys. The native client signs only the server challenge payload, verifies the trusted server/audience and intended vault, and obtains explicit user approval. The backend verifies against its own stored payload; no semantic similarity is involved. A verified proof does not itself unlock data or issue a session. Integrating a reviewed session issuer, TLS/origin/CSRF protections, secure device-key storage, revocation, and audit events remains required before real login.

Challenge storage must provide atomic NX creation and one-time consumption. The optional Redis REST adapter uses SET NX PX and a one-key atomic Lua GET/DEL operation. It makes no request until called with server-injected credentials; no environment secrets are read on import. Deployment must verify the Redis endpoint, permissions, retention, rate limits, availability and TLS. Expiring a key does not guarantee physical erasure from backups. In-memory stores in tests are fixtures only, not production persistence. Invalid signatures consume a challenge; issue a fresh challenge after failure.

Test command: `node --test src/services/v38/vaultSecurity.test.mjs`. Tests use mocked Ollama/Redis/policies and real generated test-only Ed25519 keys. They do not verify the named model, live Redis atomicity, physical browser/native UI, full workspace TypeScript compatibility or deployment. Keep the existing production login unchanged. Debug, test, review results, then request specific deployment approval.
