elizaOS separates the agent framework from the process that boots it and from the interfaces people use to control it. Most applications depend on one or two layers; they do not need the whole monorepo.

## Package boundaries

| Layer | Owner | Responsibility |
| --- | --- | --- |
| Framework | `@elizaos/core` | `AgentRuntime`, message loop, canonical types, model abstraction, memory contracts, tasks, and plugin lifecycle |
| Runnable agent | `@elizaos/agent` | Runtime composition, character and config loading, plugin resolution, the local HTTP backend, and the `eliza-autonomous` process |
| Product host | `@elizaos/app-core` | API/dashboard orchestration plus desktop, mobile, deployment, and development tooling shared by app shells |
| Interface | `@elizaos/ui` and `@elizaos/app` | React dashboard, typed API client, browser app, desktop renderer, mobile renderer, and native bridge adapters |
| Extensions | `plugins/*` | Actions, providers, evaluators, services, routes, events, models, connectors, and optional UI surfaces |
| Managed backend | `packages/cloud/*` | Hosted auth, agents, app deployment, inference, billing, storage, and the Cloud SDK |

The framework is usable on its own. Import `@elizaos/core` when you want to compose an agent inside another TypeScript application. Use `@elizaos/agent` when you want the repository's ready-made process and API. Use the app packages when you want the bundled product shell.

## Runtime composition

`AgentRuntime` owns one agent's initialized plugin graph and long-lived services. The host supplies:

- a `Character`;
- a database adapter;
- runtime settings;
- model and capability plugins;
- optional host services and transport bindings.

Plugins export a `Plugin` object. The runtime validates dependencies and registers each contribution with ownership metadata so plugins can be loaded, unloaded, or reloaded without confusing one plugin's resources with another's.

### Plugin primitives

- **Actions** describe operations the model can select and execute.
- **Providers** add current context to model input.
- **Evaluators** inspect or transform completed turns.
- **Services** are long-lived runtime singletons.
- **Model handlers** connect model types to inference implementations.
- **Routes and events** expose host integrations where a plugin needs them.

Most new product capabilities should be plugins. Add behavior to core only when it is a framework invariant shared by unrelated products.

## Message flow

A normal turn follows this order:

1. The host converts inbound content into a canonical `Memory`.
2. Providers assemble state and context for the turn.
3. The model produces a response and, when appropriate, planned action calls.
4. The planner validates arguments and executes actions through the runtime.
5. Action callbacks stream observable progress or results to the host.
6. Evaluators perform post-response processing.
7. The host persists and delivers the final response.

The detailed planner, turn controller, context renderer, and validated model-call code lives under `packages/core/src/runtime/`. Hosts should call the runtime contracts rather than reproduce that loop.

## State and persistence

The runtime uses canonical memory, entity, relationship, room, world, task, and component contracts from `@elizaos/core`. Storage is supplied by database plugins such as `@elizaos/plugin-sql`; local installations normally use PGLite, while hosted deployments use PostgreSQL-compatible storage.

User files and runtime state are separate concerns:

- `ELIZA_STATE_DIR` selects runtime state.
- `ELIZA_WORKSPACE_DIR` selects the agent workspace.
- Attachments use the agent host's content-addressed media store.
- Secrets belong in the configured secret or credential store, not in chat memories or source files.

Missing or failed data must surface as an error. A failed load is not equivalent to an empty list or a zero value.

## Configuration

Runtime settings are per agent. Inside core, `runtime.getSetting(key)` reads the character and constructor-provided settings; it intentionally does not fall through to global `process.env`, because one process may host multiple agents.

Hosts that want environment defaults fold them into the settings map during runtime construction. Plugins that explicitly support single-tenant environment fallback can use the core setting-resolution helpers.

See [Configuration](/configuration) for the product config file and links to the canonical source types.

## Tasks and background work

Core owns the task service and scheduler. Scheduled capabilities register typed tasks and durable records rather than starting unrelated polling systems. Hosts choose whether due tasks run from a local timer, a daemon, or a serverless invocation.

Diagnostic failures outside the direct action path should be reported through the runtime error-reporting boundary so the agent and operator can observe them.

## Browser, Node, and edge builds

`@elizaos/core` publishes separate Node, browser, and edge entry points. Node-only modules—filesystem access, process control, and native dependencies—must stay out of browser and edge exports. A plugin is deployable to an edge host only when all of its dependencies support that environment.

## App and native boundaries

The shared React shell lives in `@elizaos/ui`; `@elizaos/app` is the browser and renderer host. Desktop and mobile native code communicates through typed bridge adapters:

- Electrobun sources: `packages/app-core/platforms/electrobun/`
- Android sources: `packages/app-core/platforms/android/`
- iOS sources: `packages/app-core/platforms/ios/`
- Renderer bridge helpers: `packages/ui/src/bridge/`

Native bridges expose bounded capabilities. They do not move agent semantics out of TypeScript or grant a renderer arbitrary host access.

## Cloud boundary

Eliza Cloud is optional. The local runtime can operate without it. When enabled, Cloud adds hosted authentication, managed agents, inference routing, application deployment, billing, and related APIs. The Cloud UI is implemented under `packages/ui/src/cloud/`; backend routes and services live under `packages/cloud/`.
