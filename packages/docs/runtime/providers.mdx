---
title: "Runtime providers"
description: "Supply prompt context and structured state to an elizaOS agent."
---

Providers are read-only context functions. During state composition, the
runtime calls the providers selected for the turn and combines their text,
template values, and structured data.

Use a provider for information the model needs before choosing or executing an
action. Put mutations in actions or services instead.

## Define a provider

```typescript
import type { Provider } from "@elizaos/core";

export const accountProvider: Provider = {
  name: "ACCOUNT_STATUS",
  description: "Current account tier and usage",
  contexts: ["settings"],

  async get(runtime, message, state, context) {
    const account = await loadAccount(message.entityId, {
      signal: context?.signal,
    });

    return {
      text: `Account tier: ${account.tier}`,
      values: { accountTier: account.tier },
      data: { account },
    };
  },
};
```

The three result channels serve different consumers:

- `text` is inserted into model context;
- `values` supplies named template values;
- `data` exposes structured information to other runtime components.

All are optional, but a provider should return only information it can
authoritatively load.

## Register it

```typescript
import type { Plugin } from "@elizaos/core";

export const accountPlugin: Plugin = {
  name: "account-context",
  description: "Adds account context",
  providers: [accountProvider],
};
```

Providers without explicit routing default to general context. Prefer
`contexts` or `contextGate` for turn-scoped information. Reserve
`alwaysInResponseState` for cheap signals that truly belong in every response.

## Cancellation and lifecycle ownership

The runtime supplies `context.signal` to every provider execution. Providers
that perform I/O should propagate it to the database, network, or subprocess
boundary so a cancelled turn or runtime shutdown releases resources promptly.

Concurrent composition calls for the same message may share provider work. An
individual caller can cancel without interrupting other interested callers;
the shared provider signal aborts when the final caller leaves or the runtime
stops. There is no provider-local wall-clock deadline or degraded timeout
result: latency and backing-service failures remain observable instead of being
replaced with fabricated context.

The deprecated `timeoutMs` and `timeoutMode` declaration fields remain as
ignored source-compatibility shims for existing provider literals. New code
must not use them; they neither schedule a deadline nor change failure handling.

Provider `get()` must not commit external side effects. The runtime stops
awaiting a provider when its lifecycle owner cancels, but non-cooperative work
may still be running if its dependency ignores the signal.

## Selection and privacy

The current contract also supports role, destination-disclosure, and cache
gates. Treat those fields as enforcement metadata, not prompt suggestions.
Private providers are omitted from the ordinary provider list and must be
composed explicitly.

The complete, current `Provider` and `ProviderResult` interfaces live in
[`packages/core/src/types/components.ts`](https://github.com/elizaOS/eliza/blob/develop/packages/core/src/types/components.ts).
