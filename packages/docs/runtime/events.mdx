---
title: "Runtime events"
description: "Subscribe plugins to typed lifecycle and activity events emitted by an elizaOS runtime."
---

Events decouple runtime producers from plugin consumers. They are appropriate
for observation and follow-on work that does not belong in the caller's direct
return value.

## Subscribe from a plugin

```typescript
import { EventType, type Plugin } from "@elizaos/core";

export const auditPlugin: Plugin = {
  name: "audit-events",
  description: "Records completed actions",
  events: {
    [EventType.ACTION_COMPLETED]: [
      async (payload) => {
        await recordAction(payload);
      },
    ],
  },
};
```

Using `EventType` and the plugin's `events` field keeps event names and payloads
type-checked. The runtime registers and removes these handlers with the plugin
lifecycle.

## Emit an event

Runtime and plugin code can publish an event with `emitEvent()`:

```typescript
await runtime.emitEvent(EventType.MESSAGE_RECEIVED, {
  runtime,
  message,
});
```

Every standard payload includes the runtime. Event-specific payload fields are
defined in `EventPayloadMap`.

## Standard event families

The core registry currently covers:

- world, entity, room, message, channel, and voice activity;
- run, action, evaluator, and model lifecycle;
- embeddings and privacy scrubbing;
- error reporting and control messages;
- forms and UI interactions;
- command, session, agent, gateway, compaction, and tool hooks;
- pipeline-hook metrics.

Do not copy a full enum into application code or documentation. Import the
constants and consult
[`packages/core/src/types/events.ts`](https://github.com/elizaOS/eliza/blob/develop/packages/core/src/types/events.ts)
for the current names and payloads.

## Reliability rules

- Event handlers are asynchronous; await work that must finish before the
  event is considered handled.
- Make handlers safe to retry when they perform external writes.
- A diagnostic handler that must not terminate a loop should report its own
  failure with `runtime.reportError()`.
- Do not use an event when the producer requires a result from exactly one
  consumer; use a typed service method instead.

For client-facing server events, see [WebSocket events](/websocket-events).
