---
title: "Plugin database schemas"
description: "Declare Drizzle tables that the elizaOS SQL adapter migrates with a plugin."
---

A plugin can expose a Drizzle schema through its `schema` field. The SQL
adapter discovers loaded plugin schemas and runs its runtime migrator before
the plugin relies on those tables.

This feature belongs to plugins that need durable relational data beyond core
memories, entities, components, relationships, and tasks.

## Define tables

```typescript
import { index, pgTable, text, timestamp, uuid } from "drizzle-orm/pg-core";

export const bookmarks = pgTable(
  "bookmarks",
  {
    id: uuid("id").primaryKey(),
    entityId: uuid("entity_id").notNull(),
    url: text("url").notNull(),
    title: text("title").notNull(),
    createdAt: timestamp("created_at", { withTimezone: true })
      .defaultNow()
      .notNull(),
  },
  (table) => [index("bookmarks_entity_idx").on(table.entityId)],
);

export const schema = { bookmarks };
```

Use explicit foreign keys when a plugin owns both sides of a relationship.
Reference core identifiers such as `entityId`, `roomId`, or `agentId` when the
data needs that scope.

## Register the schema

```typescript
import type { Plugin } from "@elizaos/core";
import { schema } from "./schema.ts";

export const bookmarkPlugin: Plugin = {
  name: "bookmarks",
  description: "Stores owner bookmarks",
  schema,
};
```

The runtime passes loaded plugin schemas to `@elizaos/plugin-sql`. The adapter
namespaces plugin-owned tables during migration, compares the desired and
existing schema, and fails initialization when it cannot apply a required
change.

## Query through a service

Keep Drizzle access in a plugin service or repository and expose typed methods
to actions and providers. Import supported query helpers from
`@elizaos/plugin-sql/drizzle`; the schema builders are exported from
`@elizaos/plugin-sql/schema`.

Do not make route handlers or UI components calculate database results.

## Migration safety

- Treat table and column renames as destructive unless you provide an explicit
  data-preserving migration path.
- Test upgrades from a populated prior schema, not only creation from empty.
- Test constraints, indexes, foreign keys, and concurrent startup against the
  actual SQL adapter.
- Never suppress a migration failure and continue with a mismatched schema.

The runtime migration implementation and real evolution tests live under
[`plugins/plugin-sql/src/runtime-migrator`](https://github.com/elizaOS/eliza/tree/develop/plugins/plugin-sql/src/runtime-migrator)
and
[`plugins/plugin-sql/src/__tests__/migration`](https://github.com/elizaOS/eliza/tree/develop/plugins/plugin-sql/src/__tests__/migration).

If the data naturally fits an existing core store, use that store rather than
creating a parallel database model.
