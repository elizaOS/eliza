---
title: "Plugin architecture"
description: "Understand how an elizaOS plugin contributes capabilities to an agent runtime."
---

A plugin is a typed object that groups one feature's runtime contributions.
The runtime registers those contributions together and records their ownership
so a dynamically loaded plugin can also be unloaded safely.

```typescript
import type { Plugin } from "@elizaos/core";

export const weatherPlugin: Plugin = {
  name: "weather",
  description: "Adds current weather observations",
  actions: [getWeatherAction],
  providers: [weatherContextProvider],
  services: [WeatherService],
};
```

## Main extension surfaces

| Surface | Use it for |
| --- | --- |
| `actions` | Operations the planner can select and execute |
| `providers` | Read-only context for prompt and state composition |
| `services` | Long-lived clients, connections, schedulers, and stores |
| `evaluators` | Post-response evaluation |
| `models` | Model-capability handlers used by `runtime.useModel()` |
| `events` | Typed subscriptions to runtime activity |
| `routes` | Authenticated or explicitly public HTTP boundaries |
| `schema` | Drizzle tables discovered by the SQL adapter |
| `init` / `dispose` | Plugin-level setup and teardown |

The current `Plugin` interface also supports application UI contributions,
remote-mode plugins, shortcuts, tests, connector metadata, and advanced
response-handler extensions. Consult
[`packages/core/src/types/plugin.ts`](https://github.com/elizaOS/eliza/blob/develop/packages/core/src/types/plugin.ts)
instead of copying the full interface into a plugin.

## Registration lifecycle

During runtime initialization, core capabilities register first, followed by
the configured character plugins. `registerPlugin()` validates the plugin,
runs its initialization hook, registers owned components, and starts or queues
services according to runtime state.

Required initialization should throw on failure. A plugin must not register a
healthy-looking partial capability when a required credential, schema, or
service is unavailable.

Component name collisions are first-wins unless the later direct registration
declares an allowed override. Choose globally descriptive names and do not rely
on load order as hidden precedence.

## Dependencies and configuration

Use `dependencies` for required plugin relationships. Validate configuration at
initialization and read secrets through runtime settings. Package metadata for
user-configurable values belongs under `agentConfig.pluginParameters` in the
plugin's `package.json`.

## Routes

New routes should use the return-shaped `routeHandler` contract. Public routes
must declare why authentication can be bypassed, and mutating public routes
must name their out-of-band authentication mechanism. Keep business logic in a
service or use case, not in the transport adapter.

## Teardown

Service `stop()` methods release service-owned resources. The plugin's
`dispose()` hook releases resources owned by the plugin itself. Hot unload must
leave no timers, listeners, routes, or registrations behind.
