---
title: Rate Limits
description: Understand route protection and organization inference limits on elizaOS Cloud APIs.
---

elizaOS Cloud uses two independent rate-limit layers. A request can pass one
layer and still be rejected by the other.

### Route protection

Route protection controls bursts against individual API routes. It is not a
single account-wide allowance, and it is not always keyed by API key. Depending
on the route and runtime, its caller bucket can come from an API key,
authenticated user, anonymous session, source IP, or shared public fallback.
The route's configured preset or explicit limit is authoritative.

### Organization inference admission

Organization inference admission is a separate 60-second limit applied after
authentication. It covers chat, embeddings, generative media, and the public
agent MCP and A2A surfaces. API keys and sessions belonging to the same
organization share this inference budget; creating another key does not create
another budget. The organization's qualifying-credit tier and any explicit
per-organization override determine the cap.

## Organization inference tiers

The current classifier totals the USD-denominated `amount` of credit
transactions whose ledger `type` is `credit`. It excludes only transactions
with one of these exact `metadata.type` values:

- `initial_free_credits`
- `wallet_signup`
- `signup_code_bonus`

Other labels are not automatically excluded. The tier is selected from this
cumulative qualifying-credit total, not the organization's remaining balance.
These are ledger thresholds, not subscription plans.

- **Free — $0 minimum:** Completions 60 RPM, Embeddings 100 RPM, Standard 30
  RPM, Strict 5 RPM
- **Paid — $5 minimum:** Completions 120 RPM, Embeddings 200 RPM, Standard 60
  RPM, Strict 10 RPM
- **Growth — $100 minimum:** Completions 300 RPM, Embeddings 600 RPM, Standard
  120 RPM, Strict 30 RPM

An approved per-organization override can replace one or more RPM values. When
an override is present, the overridden values are authoritative even if the
organization's qualifying-credit total would otherwise select a different
value.

Endpoint classes currently map as follows:

- **Completions:** `/api/v1/chat/completions`, `/api/v1/chat`,
  `/api/v1/messages`, and Shared agent chat
- **Embeddings:** `/api/v1/embeddings`
- **Standard:** `/api/agents/{id}/mcp` and `/api/agents/{id}/a2a`
- **Strict:** image, music, prompt, sound-effect, video, speech-to-text, and
  text-to-speech generation

## Windows and resets

Inference RPM limits use a 60-second window. On the Cloudflare Worker inference
path, the Durable Object counter is keyed by organization and endpoint class,
and uses fixed windows aligned to UTC minute boundaries. The returned reset
time is the authority for the current request; do not derive it from a local
request counter.

Compatibility runtimes can enforce the same organization cap through Redis.
Generic route protection can use Cloudflare's native limiter, Redis, or a local
fallback according to the route and runtime, so its window semantics should not
be inferred from the inference limiter.

## Headers and error responses

Do not assume every endpoint emits rate-limit headers. A limiter may attach
them to successful or denied responses, but protocol adapters can translate the
response into an OpenAI-, Anthropic-, or JSON-RPC-compatible envelope. Read the
headers that are actually present on the response.

When a route returns the shared native `429` response, its body is flat:

```json
{
  "success": false,
  "error": "Too many requests",
  "code": "rate_limit_exceeded",
  "message": "Rate limit exceeded. Maximum 60 requests per 60 seconds.",
  "retryAfter": 42
}
```

The shared native response emits these headers:

- `Retry-After`: seconds to wait before retrying
- `X-RateLimit-Limit`: configured maximum for the window
- `X-RateLimit-Remaining`: requests remaining in the current window
- `X-RateLimit-Reset`: ISO 8601 timestamp when the current window resets
- `X-RateLimit-Policy`: policy that produced this response, such as
  `durable-object`, `redis`, or `in-memory`

The Worker inference path fails closed while the organization policy cache is
warming or when the authoritative limiter is unavailable. Those cases return
`503`, not `429`. Use `Retry-After` when the route emits it; warming responses
do not all preserve the same headers or JSON envelope.

The native unavailable response is:

```json
{
  "success": false,
  "error": "Rate limit unavailable",
  "code": "rate_limit_unavailable",
  "message": "The inference rate limiter is temporarily unavailable."
}
```

It includes `Retry-After: 1`, `Cache-Control: no-store`, and
`X-RateLimit-Policy: durable-object`. A cold policy cache can instead be exposed
as a protocol-specific warming error, such as `rate_limit_cache_warming`.

## Retry safely

For `429`, wait for `Retry-After` when present. Otherwise use exponential
backoff with jitter and cap the delay. The same approach is appropriate for a
retryable rate-limiter `503`; do not retry authentication, validation, or
insufficient-credit errors as though they were rate limits.

Queueing concurrent inference calls can reduce bursts, but a client-side queue
does not replace the server's organization-level counter. Coordinate queues
across workers if your application sends traffic from more than one process.

## Inspect configured caps

Authenticated callers can read the organization's current limit snapshot:

```bash
curl "https://api.eliza.app/api/v1/billing/limits" \
  -H "Authorization: Bearer $ELIZA_API_KEY"
```

The `inferenceRateLimits` item reports only the configured completions and
embeddings caps:

```json
{
  "source": "org-rate-limits",
  "state": "available",
  "completionsRpm": 120,
  "embeddingsRpm": 200
}
```

This snapshot does not contain live usage, remaining requests, reset time, or
the Standard and Strict caps. Its `state` describes whether the configured cap
source was available; it is not a usage meter.
