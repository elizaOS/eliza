title: Character JSON

A character describes how an agent presents itself and what runtime features it
requests. The canonical runtime boundary is the strict
[`characterSchema`](https://github.com/elizaOS/eliza/blob/develop/packages/core/src/schemas/character.ts);
the corresponding TypeScript interface is `Character` in
`packages/core/src/types/agent.ts`.

## Minimal character

`name` is the only required top-level field at the runtime validation boundary:

```json
{
  "name": "Research Assistant"
}
```

## Typical character

```json
{
  "name": "Research Assistant",
  "username": "research-assistant",
  "system": "Help the user investigate questions carefully and distinguish evidence from inference.",
  "bio": [
    "Synthesizes technical and scientific sources",
    "Explains uncertainty and cites evidence"
  ],
  "topics": ["research", "analysis", "technical writing"],
  "adjectives": ["careful", "clear", "curious"],
  "style": {
    "all": ["Be precise and concise"],
    "chat": ["Ask for missing constraints when they materially affect the answer"],
    "post": []
  },
  "messageExamples": [
    {
      "examples": [
        {
          "name": "{{name1}}",
          "content": { "text": "Compare these two approaches." }
        },
        {
          "name": "Research Assistant",
          "content": { "text": "I will compare their assumptions, evidence, and tradeoffs." }
        }
      ]
    }
  ],
  "postExamples": [],
  "plugins": [],
  "settings": {},
  "secrets": {},
  "advancedPlanning": true,
  "advancedMemory": true
}
```

## Top-level fields

| Field | Shape | Purpose |
| --- | --- | --- |
| `id` | UUID | Optional stable character ID. |
| `name` | string | Required display name. |
| `username` | string | Optional platform-friendly name. |
| `system` | string | Core behavior and response instructions. |
| `templates` | object | Named prompt templates; JSON characters can contain strings only. |
| `bio` | string or string[] | Biographical or capability statements; normalized to an array. |
| `messageExamples` | example groups | Demonstrations of conversational behavior. |
| `postExamples` | string[] | Demonstrations of social-post style. |
| `topics` | string[] | Subjects the character should engage with. |
| `adjectives` | string[] | Short personality descriptors. |
| `documents` | document sources | File or directory sources available to the character. |
| `knowledge` | document sources | Compatibility alias used only when `documents` is empty. |
| `plugins` | string[] | Plugin package names requested by this character. |
| `settings` | object | JSON-serializable character settings; known keys are normalized and other keys move under `extra`. |
| `secrets` | object | String, number, or boolean values; do not commit real secrets. |
| `style` | object | `all`, `chat`, and `post` instruction arrays. |
| `advancedPlanning` | boolean | Requests built-in planning capabilities. |
| `advancedMemory` | boolean | Requests built-in advanced-memory capabilities. |

Unknown top-level keys are rejected by the runtime schema. Message content and
settings deliberately allow extension data because plugins consume those
boundaries.

## Documents

Document entries use a tagged source shape:

```json
{
  "documents": [
    {
      "item": {
        "case": "path",
        "value": "/srv/eliza/knowledge/handbook.md"
      }
    },
    {
      "item": {
        "case": "directory",
        "value": {
          "path": "/srv/eliza/knowledge/reference",
          "shared": false
        }
      }
    }
  ]
}
```

The Cloud Documents API manages hosted document resources separately; do not
invent character fields such as `settings.knowledge.documentIds` unless the
plugin consuming that setting explicitly documents them.

## Model selection

Provider placement and model routing belong to runtime configuration, not the
character's top-level schema. Use the Settings UI and the
`deploymentTarget`/`serviceRouting` fields described in
[Model providers](/model-providers). A plugin may consume additional values
from `settings`, but those values are plugin contracts rather than universal
character fields.

## Cloud creation routes

Cloud offers two creation surfaces:

- `POST /api/v1/app/agents` creates a basic Cloud agent from `name`, optional
  `bio`, and optional token metadata.
- `POST /api/my-agents/characters` stores a fuller character representation.

Use [Agents](/cloud/agents) for request examples. Treat a successful Cloud
write and runtime character validation as distinct boundaries; validate a
portable character with the core schema before shipping it to another runtime.
