Model providers are plugins. The runtime loads provider plugins from explicit
configuration and from API-key environment variables declared by the
first-party registry. Runtime placement and model routing are separate: an
agent can run locally while sending inference to a remote provider.

## Automatically detected providers

The following mapping is generated from provider `registry-entry.json` files
and consumed directly by the runtime. It is the authoritative auto-detection
surface in
[`provider-plugin-map.json`](https://github.com/elizaOS/eliza/blob/develop/packages/registry/src/first-party/provider-plugin-map.json).

| Environment variable | Plugin loaded |
| --- | --- |
| `AIGATEWAY_API_KEY` or `AI_GATEWAY_API_KEY` | `@elizaos/plugin-vercel-ai-gateway` |
| `ANTHROPIC_API_KEY` | `@elizaos/plugin-anthropic` |
| `CEREBRAS_API_KEY` | `@elizaos/plugin-openai` |
| `ELIZAOS_CLOUD_API_KEY` or `ELIZAOS_CLOUD_ENABLED` | `@elizaos/plugin-elizacloud` |
| `ELIZA_CHAT_VIA_CLI` | `@elizaos/plugin-cli-inference` |
| `GEMINI_API_KEY`, `GOOGLE_API_KEY`, or `GOOGLE_GENERATIVE_AI_API_KEY` | `@elizaos/plugin-google-genai` |
| `NEARAI_API_KEY` | `@elizaos/plugin-nearai` |
| `OPENAI_API_KEY` | `@elizaos/plugin-openai` |
| `ZAI_API_KEY` or `Z_AI_API_KEY` | `@elizaos/plugin-zai` |

`CEREBRAS_API_KEY` selects the OpenAI-compatible provider implementation; it
does not load a separate Cerebras package.

<Note>
The registry map defines automatic loading, not every provider plugin that can
be installed explicitly. A provider absent from this table must be installed
and enabled deliberately; an arbitrary `*_API_KEY` variable does not cause the
runtime to discover a package.
</Note>

## Configure credentials

Set secrets in the process environment, the app's credential UI, or
`env.vars` in the canonical config file:

```json5
// ~/.local/state/eliza/eliza.json
{
  env: {
    vars: {
      ANTHROPIC_API_KEY: "<anthropic-api-key>",
    },
  },
}
```

The default state directory is `~/.local/state/eliza`. `ELIZA_STATE_DIR`
overrides it, and `ELIZA_CONFIG_PATH` can point directly at a different config
file. Avoid committing secrets or placing them in shared project files.

## Select the active route

The current topology is persisted in three top-level config fields:

- `deploymentTarget` says where the runtime runs.
- `linkedAccounts` records accounts available to that runtime.
- `serviceRouting` assigns capabilities such as `llmText` to a backend.

The provider-switching API and settings UI write those fields together. A
minimal direct-provider selection looks like this:

```json5
{
  deploymentTarget: {
    runtime: "local",
  },
  serviceRouting: {
    llmText: {
      backend: "openai",
      transport: "direct",
    },
  },
  agents: {
    defaults: {
      model: {
        primary: "@elizaos/plugin-openai",
      },
    },
  },
}
```

Prefer the Settings UI or provider-switch API when changing an existing
installation; they normalize linked-account and routing state and clear fields
that no longer apply.

## Enable or disable a provider explicitly

`plugins.allow` is additive. Short IDs are normalized to
`@elizaos/plugin-<id>` when the runtime builds its load set:

```json5
{
  plugins: {
    allow: ["openai"],
    entries: {
      openai: { enabled: true },
      anthropic: { enabled: false },
    },
  },
}
```

When any provider entry is explicitly enabled, provider entries become the
selection boundary: other automatically detected providers are not loaded
unless their entry is also enabled. Restart the runtime after changing the
provider load set.

## Local inference

Embedded local inference is supplied by
`@elizaos/plugin-local-inference`. On-device and packaged builds gate it by
platform and build profile; it is not enabled merely because a model directory
exists. Use the app's local-inference settings for supported packaged builds,
or enable the plugin explicitly in a source deployment and follow its README
for native dependencies and model assets.

## Troubleshooting

If the agent reports that no provider is loaded:

1. Confirm the credential is present in the runtime process, not only in a
   shell or client process.
2. Check that `plugins.entries.<id>.enabled` is not `false`.
3. Check `deploymentTarget` and `serviceRouting`; remote and cloud modes can
   intentionally remove direct provider plugins from the local load set.
4. Inspect startup logs for plugin import or core-version compatibility errors.
5. Use the generated provider map above to verify that the credential name
   really participates in automatic loading.

See [Configuration](/configuration) for config-file loading and links to the
canonical config types.
