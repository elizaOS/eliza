## Recovery

[`production-ledger-recovery-20261023.sql`](production-ledger-recovery-20261023.sql) is generated by [`production-ledger-recovery-20261023.ts`](production-ledger-recovery-20261023.ts) from the canonical journal. The test pins the committed SQL to the generator's output. It runs as one transaction:

1. Locks the ledger and refuses any state other than the reviewed 373 rows, matched by exact ids and hashes.
2. Archives rows 371–373 into `drizzle.__drizzle_migrations_retired_20261023`.
3. Applies the 143 remaining canonical migrations in journal order.
   - For 14 superseded intermediate CHECKs, the body becomes a `CHECK (true) NOT VALID` placeholder.
   - Those intermediate shapes are redefined later in the same transaction.
   - Historical rows written by the out-of-order Gmail and grant migrations cannot satisfy them.
4. Writes canonical receipts for all 149 journal entries after the prefix.
5. Aborts if the ledger is not exactly 519 rows or if any placeholder survives.

- The recovery commits in about 3 s.
- `validateAppliedMigrationLedger` from main reports 519 applied and 0 pending.
- Compared with a database built from all 519 canonical migrations, every canonical object matches except these 36:
  - `public.approval_requests` and `public.approval_request_events`: the agent runtime's tables, by design since #18321. Cloud uses `cloud_approval_requests`, which matches exactly.
  - The `uuid` id columns on the runtime-owned memory tables (`session_summaries`, `memory_access_logs`, `long_term_memories`).
  - 10 CHECKs and 1 trigger function that are semantically identical but formatted differently (parenthesisation and whitespace).
- No constraint ends up unvalidated that is validated in canonical.
- Re-running the recovery on the repaired copy aborts with `ledger_shape_mismatch` and changes nothing.
